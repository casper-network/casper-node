# VM2 Smart Contracts

Casper's second-generation virtual machine (VM2) modernizes how smart contracts are authored, deployed, and called. This note distills what changes relative to the original `casper-contract` (VM1) toolchain, shows how the `#[casper]` attribute family shapes VM2 code, and walks through the most relevant pieces of `casper_contract_sdk` and `casper_contract_sdk_contrib`.

## VM2 vs VM1 at a Glance
| Topic | VM1 (`casper-contract`) | VM2 (`casper_contract_sdk`) |
| --- | --- | --- |
| Entry points | `#[no_mangle] pub extern "C"` functions with manual `runtime::get_named_arg` handling | Ordinary methods inside `#[casper]` impl blocks; serialization, argument extraction, return handling, and Wasm exports are generated automatically) |
| State persistence | Contract state stored via explicit URefs and `storage::{read,write}` calls | `#[casper(contract_state)]` structs derive `BorshSerialize`/`BorshDeserialize` and are read/written for you) |
| Serialization | CLValue/`RuntimeArgs` everywhere; no default schema | Borsh positional ABI by default with opt-in named CLValue ABI) |
| ABI metadata | Developers build `EntryPoints` structures manually | ABI manifest and `Ref` handles generated by macros for contracts and traits) |
| Cross-contract calls | `runtime::call_contract` with raw `RuntimeArgs` | Typed builders (`ContractBuilder`, `ContractHandle`) plus generated `Ref` helpers) |
| Eventing | `runtime::emit_event` with manual topic/payload | `#[casper(message)]` structs + `casper::emit_message`s:16`) |
| Reusable patterns | Mostly hand-written libraries | `casper_contract_sdk_contrib` ships composable traits (Ownable, AccessControl, Pausable, CEP-18) built on VM2 macros |

## The `#[casper]` Attribute Family

### Contract State
Annotate a struct with `#[casper(contract_state)]` to make it the persisted state of a contract. The macro generates:
- Borsh (de)serialization and a type UID.
- A companion `Ref` type (`MyContractRef`) used by the SDK when building call data.
- ABI metadata emitted through `linkme`.

```rust
use casper_contract_sdk::prelude::*;

#[casper(contract_state)]
pub struct Counter {
    value: u64,
}
```

### Entry Points
Wrap `impl` blocks in `#[casper]` to turn public methods into exported entry points. Receivers control how state is treated:
- `&mut self` loads state and writes it back after the call.
- `&self` loads state but does not persist changes.
- No receiver means a pure function entry point. Use `#[casper(ignore_state)]` on static methods when you want to handle storage manually (the macro keeps the helper static and avoids implicit reads).

Common method-level attributes:

| Attribute | Effect |
| --- | --- |
| `#[casper(constructor)]` | Ensures the contract is uninitialized, runs the method, and stores the returned state. Constructors cannot take `self`. |
| `#[casper(payable)]` | Allows non-zero transferred value; without it, calls trap if tokens are sent. |
| `#[casper(private)]` | Skips Wasm export so the method is only callable from Rust. |
| `#[casper(rollback_on_error)]` | Expects the method to return `Result`. If it is `Err`, the VM marks the call as a rollback. |
| `#[casper(ignore_state)]` | Skips automatic state load/save and keeps the generated helper method static—handy for upgrade hooks that call `casper::read_state`/`write_state` themselves. |
| `#[casper(abi_convention = ...)]` | Overrides the struct-level ABI convention (e.g., switch a single entry point to named CLValue arguments). |

```rust
/// This contract implements a simple flipper.
#[casper(contract_state)]
#[derive(Default)]
pub struct Flipper {
    /// The current state of the flipper.
    value: bool,
}

#[casper]
impl Flipper {
    #[casper(constructor)]
    pub fn new(init_value: bool) -> Self {
        Self { value: init_value }
    }

    #[casper(constructor)]
    pub fn default() -> Self {
        Self::new(Default::default())
    }

    pub fn flip(&mut self) {
        self.value = !self.value;
    }

    pub fn get(&self) -> bool {
        self.value
    }
}
```

- `new` - method is marked as a constructor and a Transaction can be sent that will perform installation. No session code is necessary to setup a contract. The contract itself with all its Wasm exports is the smart
contract. An attempt to execute a constructor will fail as the state is already persisted in the global state.
- `default` - another constructor with no arguments
- `flip` - When called, will load `Flipper` state from the global state, mutate it (inside the VM memory), then persist it again.
- `get` - An entrypoint that takes no arguments and does not mutate state (`&self`). It can be used with the sandbox RPC to retrieve the value off-chain.

Each exported method gets a helper on the generated `CounterRef` so you can build typed call data or invoke it through a `ContractHandle`.

### Traits as Interfaces
Applying `#[casper]` to a trait produces:
- A `TraitNameRef` type implementing `ContractRef`.
- Generated dispatchers that load state and call the trait methods on your concrete type.
- A trait-specific macro you invoke inside the implementing crate to wire up entry points.

Use `#[casper(export = true)]` on the trait if the dispatcher macro should be public (as done in `casper_contract_sdk_contrib::ownable`). When implementing a trait defined in another crate, point the macro to that crate with `#[casper(path = their::module)]` so the correct helper macro is used.

This allows users to use trait implementations to define a behavior of a smart contract with zero extra effort.

```rust
#[casper]
pub trait Greeter {
    fn greet(&self, name: String) -> String;
}

#[casper(contract_state)]
pub struct GreeterContract {
    prefix: String,
}

#[casper]
impl Greeter for GreeterContract {
    fn greet(&self, name: String) -> String {
        format!("{} {name}", self.prefix)
    }
}
```

### Messages and Events

Use `#[casper(message(topic = "...")]` on a struct to create an event payload. The macro implements `casper_contract_sdk::Message` so you can emit it with `casper::emit_message`:

```rust
#[casper(message(topic = "CounterUpdated"))]
pub struct CounterUpdated {
    pub new_value: u64,
}

#[casper]
impl Counter {
    pub fn increment(&mut self) {
        self.value += 1;
        casper::emit_message(CounterUpdated { new_value: self.value }).unwrap();
    }
}
```

A `topic` attribute can be omitted and the topic name will defaul to the struct name:

```rust
#[casper(message)]
pub struct CounterUpdated {
    pub new_value: u64,
}
```

## Working with `casper_contract_sdk`

The SDKs everything needed to write contracts and off-chain clients:
- `prelude::*` offers `alloc`/`std` collections, formatting, the `casper` module, and helper macros- `casper::` mirrors familiar host calls—`get_caller`, `create`, `call`, `read`, `write`, `emit_message`, etc.- `ContractBuilder` and `ContractHandle` simplify deployment and invocation with typed call data.
- `serializers` define ABI conventions. Positional Borsh is the default, but you can opt into named CLValue payloads for compatibility with existing tooling.

Example session:

```rust
use casper_contract_sdk::{
    prelude::*,
    types::{Address, U256},
    ContractHandle,
};
use casper_contract_sdk_contrib::cep18::{CEP18Ext, MintableExt};
use vm2_cep18::TokenContractRef;

#[casper(export)]
pub fn call(address: Address) -> String {
    let handle = ContractHandle::<TokenContractRef>::from_address(address);
    // Mint tokens, then check the balance of the account that called this contract
    handle
        .call(|contract| contract.mint(Entity::Account([99; 32]), U256::from(100u64)))
        .expect("Should call")
        .expect("Should mint");

    let balance_result = handle
        .call(|contract| contract.balance_of(Entity::Account([99; 32])))
        .expect("Should call");

    assert_eq!(balance_result, U256::from(100u64));

    let name_result = handle
        .call(|contract| contract.name())
        .expect("Should call");
    log!("Name: {name_result:?}");
    let transfer_result = handle
        .call(|contract| contract.transfer(Entity::Account([100; 32]), U256::from(100u64)))
        .expect("Should call");

    log!("Transfer: {transfer_result:?}");

    log!("Success");

    name_result
}
```

## Using `casper_contract_sdk_contrib`

The contrib crates reusable building blocks built on the VM2 macros:
- `ownable`: owner gating with `#[casper(rollback_on_error)]` protected methods
- `access_control`: role-based access enforcement
- `pausable`: pause/unpause pattern
- `cep18`: reference implementation of the CEP-18 fungible token

To consume one, implement the exported trait for your contract state using the generated helper macro:

```rust
use casper_contract_sdk_contrib::ownable::{Ownable, OwnableState};

#[casper(contract_state)]
pub struct Vault {
    owner: OwnableState,
    balance: u64,
}

#[casper(path = casper_contract_sdk_contrib::ownable)]
impl Ownable for Vault {
    fn state(&self) -> &OwnableState {
        &self.owner
    }
    fn state_mut(&mut self) -> &mut OwnableState {
        &mut self.owner
    }
}
```

You can layer multiple contrib traits; see `smart_contracts/contracts/vm2/vm2-trait/src/lib.rs` for a contract mixing `Ownable`, `AccessControl`, and custom traits.

## Migration Tips from VM1
- Map VM1 entry points to methods: replace `#[no_mangle] extern "C" fn call()` with a `#[casper] impl` and mark constructors explicitly.
- Move typed state into a `#[casper(contract_state)]` struct instead of managing URefs directly.
- Replace `runtime::call_contract` + `RuntimeArgs` with `ContractHandle::call` builders. If you need to maintain a named-argument interface, set `#[casper(abi_convention = casper_contract_sdk::serializers::AbiConvention::Named)]` on your state or specific methods.
- Revisit error handling: have methods return `Result` and enable `#[casper(rollback_on_error)]` when you want trap-like semantics without panicking.
- For events, switch from manual `runtime::emit_event` payloads to `#[casper(message)]` structs and `casper::emit_message`.

## Contract schema and bundles

- Schema is the complete definition of all types, entrypoints, argument names used in the smart contract source code. It contains all the identifiers, sources, types, locations and so on.
- Bundle is the compacted binary representation of the schema that only contains relevant information for discoverability. It does not preserve identifiers and names only type UIDs for each used type.

To build a smart contract and extract contract schema incl. contract bundle

```sh
cargo run -p vm2-cargo-casper -- build -p vm2-hello-world
```

This will perform 3 steps

- Step 1: Build contract schema. This will build your contract targeting native (x86_64/arm64/etc.), then load up the shared library, and extract all the gathered source code information.
- Step 2: Build smart contract targeting `wasm32-unknown-unknown`. Resulting `.wasm` blob will not contain any run time type information used for `Step 1`. Gathering schema information does not add overhead to the binary. The build is performed with opinionated flags incl. `--release`
- Step 3: Apply optimizations. This will run wasm through `wasm-strip`

After all the steps are performed build artifacts are reported:

```
✅ Completed.
WASM built at: $PATH/target/wasm32-unknown-unknown/release/vm2_hello_world.wasm
Schema built at: $PATH/target/wasm32-unknown-unknown/release/vm2_hello_world.json
Bundle built at: $PATH/target/wasm32-unknown-unknown/release/vm2_hello_world.bundle
```

Bundle can be supplied together in an install transaction and the host will take care of updating type information in the global state. The type definitions are global and on each subsequent smart contract extends the global database of type definitions.
